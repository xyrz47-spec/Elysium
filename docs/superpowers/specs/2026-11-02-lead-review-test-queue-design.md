# 총괄 검토·테스트 대기열·에이전트 창 설계
날짜: 2026-11-02

## 1. 의도와 이유
- 사용자는 Claude Opus를 총괄로, Gemini 3.8 Flash High 여러 개를 워커로 돌려 큰 저장소(Plexus Mod Loader, Minecraft 모드 로더, Gradle 기반)를 작업한다.
- 현재 Elysium의 Gemini 워커는 파일 수정만 가능하고 명령 실행이 막혀 있다(`--settings {"permissions":{"deny":["command(*)"]}}`, 실제 거부를 확인함). 그래서 워커가 자기 작업을 빌드·테스트로 확인할 수 없다.
- 예전에 Claude가 이를 우회하려고 셸에서 `agy`를 직접 띄웠고, 시간 제한·중지·비용 집계를 벗어나 타임아웃과 고아 프로세스가 생겼다. 워커가 명령이 필요할 때 쓸 정식 경로를 만들어 이 문제를 없앤다.
- 게임 창을 띄우는 테스트는 동시에 여러 개 돌리면 서로 방해되므로 대기열이 필요하다.
- 사용자는 작업을 지켜보다가 문제를 총괄에게 알려 바로잡고 싶어 하고, 지금 오른쪽 창(폭 320px)은 너무 작다.

## 2. 목표
- 워커 명령 요청과 총괄 검토 (사용자 결정): 워커는 직접 실행하지 못하고 총괄에게 요청한다. 총괄은 "이것만 허용", "거부", "비슷한 명령 자동 허용(이후 검토 없이)", "모든 명령 자동 허용(이후 검토 없이)" 중 하나를 고른다.
- 게임 테스트 대기열 (사용자 결정): 창을 띄우는 테스트는 대기열에 등록하고, 자리가 있으면 실행, 없으면 기다리거나 다른 일을 먼저 한다. 동시 실행 수는 사용자가 정한다. 사람이 직접 닫아야 끝나는 게임 테스트(`runClient` 같은 수동 확인 작업)는 워커가 요청할 수 없으며 스스로 끝나는 작업만 요청한다. 대기열 카드에 실행 중인 테스트만 끄는 버튼을 둔다. 명령 도구가 이미 있는 AI의 게임 테스트도 대기열을 쓰게 한다.
- 대기 중 행동 (사용자 결정): 남은 다른 작업이 있으면 그 일을 하고, 없으면 기다린다. 워커가 스스로 판단한다.
- 판단은 어디서든 JEV를 활용하고, 총괄의 판단이 필요한 부분은 총괄도 함께 판단한다 (사용자 결정).
- 사용자와 총괄의 소통 (사용자 결정): 오른쪽 창에서 각 워커가 무엇을 하는지 보고, 특정 워커 문제나 전체 문제를 총괄에게 보내면 총괄이 그 부분을 바꾼다. 총괄은 계획에 변수가 생기거나 물어볼 일이 생기면 사용자에게 질문할 수 있다. 총괄의 질문은 휴대폰(원격 제어)에서도 조회하고 답변할 수 있다.
- 오른쪽 창 확대 (사용자 결정): 시안 A안. 기본 폭 560px, 경계를 끌어 조절, 크기를 기억한다. 대화는 좁아진 상태로 함께 보인다. 에이전트와 곁질문을 포함한 모든 탭에 적용한다.
- 워커 별도 창 (사용자 결정): 워커마다 다른 모니터로 옮길 수 있는 별도 OS 창으로 띄운다. 배경과 UI는 앱의 기본 배경·UI를 따른다.
- 워커 그룹 (사용자 결정): 둘 이상의 워커를 한 그룹으로 묶어 한 작업을 서로 이야기하며 역할을 나눠 진행할 수 있다. 사용자가 요청문에 직접 적었으면 그대로 묶고, 알아서 하라고 했으면 총괄이 묶는다.

## 3. 비목표
- 명령 샌드박스 구현은 하지 않는다. 명령은 사용자 권한으로 실행된다.
- 단일 에이전트 실행, 답변 병합 팀, 회의, 토론 모드의 동작은 바꾸지 않는다.
- 이미 명령 도구가 있는 AI(Claude 총괄의 통합 단계, 워커로 배정된 Claude·Codex 등)의 일반 명령 실행 방식은 바꾸지 않는다. 다만 게임 테스트는 대기열을 쓰도록 하며, 지시와 패턴 차단에 의존하므로 100% 막지는 못한다는 한계를 명시한다 (사용자 결정).
- 다른 대화(작업) 간 자동 허용 규칙 공유는 하지 않는다.
- 휴대폰(원격 제어)에서 총괄 질문 조회·답변 외의 다른 기능(전체 지시 보내기, 별도 창, 대기열 조작)은 이번 범위가 아니다 (사용자 결정).
- 그룹끼리 직접 대화하는 기능은 만들지 않는다. 그룹 사이 조율은 총괄이 맡는다. 휴대폰에서 그룹 대화를 보는 기능도 이번 범위가 아니다 (작성자 판단).

## 4. 하면 실패인 것
- 워커가 어떤 경로로든 검토 없이 직접 명령을 실행하는 것.
- "모든 명령 자동 허용"이어도 게임 테스트가 대기열을 건너뛰는 것. 명령 도구가 이미 있는 AI가 대기열을 건너뛰고 게임 테스트를 실행하는 것(단, 지시와 패턴 차단 한계 내에서 적용) (사용자 결정).
- `;`, `|`, `&`, `>`, 백틱, `$(`, 줄바꿈으로 이어 붙인 명령이 "비슷한 명령" 규칙을 타고 통과하는 것.
- 사용자가 중지했는데 명령이나 게임이 계속 도는 것(프로세스 트리까지 끝낸다).
- 총괄의 질문에 답이 없다고 관련 없는 워커까지 멈추는 것.
- 큐 대기 시간 때문에 워커가 시간 초과로 실패하는 것.
- 별도 창이 메인과 다른 색·배경으로 보이는 것.
- 사용자가 요청문에 적은 그룹 구성을 총괄이 바꾸는 것.

## 5. 제약
- 코드 사실: `src-tauri/src/orchestrator.rs`의 `run_team_work`가 병렬 작업을 돌린다(`Team`, `TeamAgent`, `run_engine_as`, `AgentLine.deliver`로 작업 중 메시지 전달). `src-tauri/src/engines.rs`의 `RunSpec.resume`이 Antigravity에서는 `--conversation`으로 이어진다. `src-tauri/src/api_agent.rs`의 `powershell(root, command, secs)`가 트리 종료와 출력 자르기를 갖춘 PowerShell 실행기다(지금은 비공개 함수). `src-tauri/src/jev.rs`의 `jev::ask`가 JEV 호출이고 `orchestrator.rs`에 판단 함수 선례가 있다(`failure_transient` 등, choice 질문과 `jev::prob`). `audit::record`가 감사 기록이다. `src-tauri/src/settings.rs`의 `Settings`는 `serde(default)`라 필드 추가가 안전하다.
- 프론트 사실: `src/components/Tools.tsx`가 오른쪽 창, `src/store.tsx`가 `task:agent`, `task:agent-delta`, `task:agent-activity` 이벤트로 상태를 모은다. 출력 이력은 프런트 상태에만 있고 백엔드에 없다. `.tools-panel`은 `position:absolute; width:320px`로 대화 위에 떠 있고 `.app`은 3열 grid다. 테마는 `src/lib/theme`, 토큰은 `src/tokens.css`다.
- Tauri: `src-tauri/capabilities/default.json`은 `windows: ["main"]`뿐이라 새 창 라벨을 추가해야 한다. CSP는 `tauri.conf.json`에 있다. 지금 `src-tauri`에 닫기·종료 처리가 없으므로 메인 창에 닫기 처리를 추가해야 한다 (작성자 판단).
- 원격 제어: 기존 원격 승인과 같은 방식으로 `src-tauri/src/remote.rs`에 총괄 질문 조회·답변 경로를 추가하고(`/api/approvals`, `/api/approvals/{id}`가 선례, 경로 이름은 구현자 결정), `mobile/` 앱에 질문 표시와 답변 화면을 추가한다 (사용자 결정).
- 작업 공간: 큰 저장소의 워커는 `git worktree`(.gitignore에 걸린 파일 제외)에서 일하고, 작은 폴더는 사본에서 일한다. 이 작업은 현재 브랜치의 커밋 전 변경(`teamwork::prepare_dirs`, `requested_team`)을 전제로 한다.
- 빌드 도구 제약: Plexus는 Gradle 데몬을 끄지 않으며, 게임이 데몬의 자식이면 PowerShell 트리 종료로 끝나지 않을 수 있다(코드에서 추론, 미검증). 구현 초기에 실제로 시험한다. 게임이 남으면 게임 테스트에만 `--no-daemon`을 붙이고, 실제 실행한 명령을 판단 기록과 감사 기록에 그대로 남긴다. 일반 명령은 고치지 않는다 (작성자 판단).
- 저장소 규칙: 사용자에게 보이는 UI 문자열은 `__AGY__("Context: ... | Intent: ... | Tone: ... | Constraints: ... | Target Language: Korean")` 자리표시자로 쓰고 `just-code-claude --replace-in-file <path> -m "3.8 flash" -e medium`으로 바꾼다. 커밋 메시지는 `just-code-claude --commit`으로 만든다.
- 코드 사실: 회의 모드(`orchestrator.rs`의 `council_plan`, `council_system`, `council_followup`, `council_full`, `COUNCIL_MSG_CHARS`)는 라운드마다 서로의 발언을 읽고 대화하는 구조지만 `!p.work`에서만 돌아 답변만 내고 파일은 고치지 못한다. 하위 작업 형식은 `teamwork::Part`(`title`, `task`, `files`)와 `teamwork::parse_parts`, 나누기 지시는 `teamwork::split_prompt`다.

## 6. 동작 설계

### 6.1 워커 요청 경로 (작성자 판단)
- `agy`는 Elysium 도구를 호출할 수 없으므로 차례 기반 프로토콜을 쓴다. 워커는 답 끝에 ```` ```elysium-request ```` 펜스 블록으로 JSON을 낸다: `{"requests":[{"command":"...","why":"...","kind":"command|window","timeout_sec":600}]}`. 시스템 지시로 이 형식을 알려 준다.
- Elysium이 차례가 끝나면 블록을 읽고 처리한 뒤, 결과를 담아 같은 대화를 `--conversation`으로 이어 다음 차례를 시작한다. 블록은 사용자에게 보이는 본문과 통합 AI에게 넘기는 요약에서 뺀다.
- 블록이 없고 처리 중인 테스트도 없으면 그 워커는 끝난다. 차례 수 상한을 둔다(값은 구현자 결정).
- 블록 JSON이 깨졌으면 오류를 돌려주고 다시 쓰게 한다.
- 명령 도구가 이미 있는 AI(Claude 총괄의 통합 단계, 워커로 배정된 Claude·Codex 등)가 대기열을 쓰는 경로는 Antigravity 워커와 같은 `elysium-request` 요청 블록과 차례 재개이며, 세션을 이어 쓸 수 없는 엔진은 이 경로를 쓸 수 없으니 시스템 지시만 적용한다 (작성자 판단).
- `agy mcp` 명령이 있어 MCP 방식도 가능하지만, 포트·서버가 늘고 차례 기반이면 기존 재개 기능으로 충분해서 택하지 않았다. 구현 초기에 실제 `agy`로 재개 왕복을 먼저 검증한다.

### 6.2 판단 흐름 (JEV + 총괄)
순서:
1. 창 판정: 워커의 `kind`, JEV 판단, 규칙에 저장된 값, 총괄의 판단 중 하나라도 window면 게임 테스트로 처리한다. 자동 허용 상태여도 이 판정은 항상 돈다. JEV를 못 쓰면 나머지 값으로 정한다. 사람이 직접 닫아야 끝나는 게임 테스트(`runClient` 같은 수동 확인 작업)는 워커가 요청할 수 없으며, 워커는 스스로 끝나는 작업만 요청하고 수동 작업 요청은 총괄이 거부한다 (사용자 결정).
2. 자동 허용 확인: "모든 명령 자동 허용"이 켜졌거나 "비슷한 명령" 규칙에 맞으면 검토 없이 실행 단계로 간다.
3. JEV 1차 판단: 위험도, 요청 작업 범위 안인지, 읽기 전용인지를 묻는다. 분명히 안전하면 총괄을 부르지 않고 "이것만 허용"으로 처리한다 (작성자 판단: 총괄 호출 비용을 줄인다). 임계값은 구현자 결정.
4. 그 밖에는 총괄이 JEV 의견을 함께 받아 판단한다. 자동 허용 범위를 넓히는 "비슷한 명령"과 "모든 명령"은 총괄만 고를 수 있다 (작성자 판단). 총괄의 답 형식: `{"decision":"once|deny|similar|all|ask_user","pattern":"...","window":false,"reason":"...","question":"...","options":[...],"workers":[...]}`.
5. JEV를 못 쓰면 총괄만 판단한다. 총괄 호출이 실패하거나 답 JSON의 `pattern`, `window`, `workers` 등을 해석할 수 없으면 거부로 처리한다 (작성자 판단).
- 같은 작업의 검토는 직렬로 처리해 앞선 판단으로 생긴 규칙이 다음 요청에 바로 적용되게 한다. 단, 검토 직렬화는 질문을 기다리는 동안 유지하지 않는다. `ask_user`가 나오면 검토 차례를 놓아 다른 워커의 검토가 계속되게 한다. 질문을 일으킨 요청은 답이 올 때까지 보류한다 (작성자 판단).
- 질문 관련 워커는 총괄 답의 `workers` 필드(워커 번호 목록)로 지정하고, 비었으면 요청한 워커만 해당한다. 관련 워커는 진행 중인 차례를 끊지 않고 다음 차례만 보류한다. 총괄이 명시적으로 워커 메시지를 보내면 그때만 `AgentLine.deliver`로 차례를 끊는다 (작성자 판단).
- 워커 명령 문자열은 데이터로 취급하고 총괄 프롬프트에서 지시로 해석하지 않게 한다.

### 6.3 자동 허용 규칙 (작성자 판단)
- 규칙은 그 작업(task) 안에서만 유효하고, 다음 작업은 처음부터 검토한다. 사용자가 이 판단에 이의를 제기하지 않았다.
- "비슷한 명령"은 앞부분 토큰 일치로 판단한다. `.\`, `./`와 `.bat`, `.cmd`, `.exe`는 정규화한다.
- 이어 붙이는 문자(`;`, `|`, `&`, `>`, 백틱, `$(`, 줄바꿈)가 든 명령은 규칙에 맞지 않은 것으로 보고 다시 검토한다.
- `powershell`, `pwsh`, `cmd`, `bash`, `sh`, `python`, `node`, `iex`, `Invoke-Expression`, `Start-Process`처럼 임의 명령을 실행하는 프로그램만 적은 패턴은 받지 않고 "이것만 허용"으로 낮춘다.
- 판단 기록 카드에 사용자가 "모든 명령 자동 허용"과 "비슷한 명령" 규칙을 끄는 버튼을 둔다. 끄면 다음 요청부터 다시 검토한다. 실행 중인 명령은 끊지 않는다 (작성자 판단).

### 6.4 명령 실행
- 워커의 작업 공간을 현재 폴더로 `api_agent::powershell`을 공용화해 쓴다. 시간 제한은 `timeout_sec`를 범위 안으로 자른다(범위는 구현자 결정). 작업이나 워커를 중지하면 트리째 끝낸다.
- 헤드리스 명령: 동시 실행 제한을 두지 않는다(`kind`는 `command`, `window` 두 가지). 총괄이 검토하면서 필요하면 `--max-workers` 같은 인자를 붙이라고 워커에게 지시할 수 있다. 이 때문에 빌드 부하가 겹칠 수 있고, 성능 측정 작업은 부하의 영향을 받을 수 있다 (작성자 판단).
- 게임 강제 종료 대비: Plexus는 Gradle 데몬을 끄지 않으며, 게임이 데몬의 자식이면 PowerShell 트리 종료로 끝나지 않을 수 있다(코드에서 추론, 미검증). 구현 초기에 실제로 시험한다. 게임이 남으면 게임 테스트에만 `--no-daemon`을 붙이고, 실제 실행한 명령을 판단 기록과 감사 기록에 그대로 남긴다. 일반 명령은 고치지 않는다 (작성자 판단).
- 결과(종료 코드와 잘린 출력)를 다음 차례 프롬프트로 돌려준다. 거부면 이유를 돌려준다.
- 모든 요청과 판단(누가 판단했는지 포함)과 결과를 `audit::record`와 UI 기록에 남긴다. 명령 판단 기록은 작업이 끝나도 `message_data`에 저장해 대화 기록에서 볼 수 있게 한다. 이 정보는 `task:done`에서 지워지는 실시간 상태(`src/store.tsx`)와 별개로 남는다 (작성자 판단).

### 6.5 게임 테스트 대기열
- 앱 전체에 하나의 FIFO 대기열을 둔다(`AppState`) (작성자 판단: 다른 대화의 게임 창과도 겹치면 안 된다).
- 설정 `testSlots`: 기본 1 (작성자 판단), 범위 1~8 (작성자 판단). 설정 창과 대기열 카드에서 바꾼다. 늘리면 바로 다음 대기 항목이 시작되고, 줄여도 실행 중인 테스트는 끊지 않는다.
- 사람이 직접 닫아야 끝나는 게임 테스트(`runClient` 같은 수동 확인 작업)는 워커가 요청할 수 없다. 워커는 스스로 끝나는 작업만 요청하고, 수동 작업 요청은 총괄이 거부한다 (사용자 결정).
- 대기열 카드의 실행 중 항목에 그 테스트만 끄는 버튼을 둔다. 이 버튼은 워커를 중지하지 않고, 워커에게는 사용자가 테스트를 껐다는 결과를 돌려준다 (사용자 결정).
- 명령 도구가 이미 있는 AI(Claude 총괄의 통합 단계, 워커로 배정된 Claude·Codex 등)의 게임 테스트도 대기열을 쓰게 한다. 방법은 시스템 지시와, Claude에는 `--disallowedTools` 등 가능한 범위의 차단 규칙이다. 지시와 패턴 차단에 의존하므로 100% 막지는 못한다는 한계를 명시한다 (사용자 결정).
- 자리가 없으면 워커에게 "대기열 N번째이며, 남은 다른 작업이 있으면 진행하고 없으면 차례를 끝내라"고 돌려준다. 워커가 스스로 판단한다 (사용자 결정).
- 워커가 요청 없이 차례를 끝냈는데 처리 중인 테스트가 있으면 Elysium이 프로세스 없이 기다렸다가 결과를 담아 대화를 잇는다. 진행 중인 차례가 있으면 결과는 다음 차례에 전달한다.
- 게임 테스트에도 `timeout_sec` 상한을 적용한다. 값은 구현자 결정이되 Plexus `frameBenchmark`(게임 창 12번, 창 사이 20초 대기)가 끝날 수 있어야 한다. 시간을 넘기면 프로세스를 끝내고 자리를 돌려준다 (작성자 판단).
- 큐 대기와 테스트 실행 시간은 워커 시간 제한에 넣지 않는다. 중지하면 큐에서 빠진다.
- UI에 실행 중 항목과 대기 순번을 보인다.

### 6.6 사용자와 총괄의 소통
- 총괄: 요청 글에서 지정하지 않으면 `Team.synth`가 총괄을 맡는다 (작성자 판단).
- 총괄은 분할과 통합 사이에도 필요할 때 세션을 이어(`--resume`) 호출한다. `resumable()`이 아닌 엔진이 총괄이면 호출마다 맥락(요청, 계획, 워커 상태, 지금까지의 판단)을 다시 만들어 넘긴다 (작성자 판단). 호출은 작업 단위로 직렬화한다.
- 입력: 총괄 카드의 전체 지시 칸, 워커 카드의 "이 워커 문제를 총괄에게 알리기".
- 총괄의 답은 JSON 행동 목록이다: 사용자에게 할 말, 워커별 메시지(`AgentLine.deliver`로 전달), 워커 중지, 사용자 질문.
- 워커 차례가 끝날 때 JEV가 계획에서 벗어났거나 막혔는지 판단하고, 그렇다면 총괄을 부른다 (작성자 판단).
- 총괄 질문:
    - 총괄 카드에 보기 버튼과 직접 입력으로 표시한다.
    - 휴대폰(원격 제어)에서도 답할 수 있어야 한다. 기존 원격 승인과 같은 방식으로 `src-tauri/src/remote.rs`에 총괄 질문 조회·답변 경로를 추가하고(`/api/approvals`, `/api/approvals/{id}`가 선례, 경로 이름은 구현자 결정), `mobile/` 앱에 질문 표시와 답변 화면을 추가한다. 보기 선택과 직접 입력을 모두 지원한다. PC와 휴대폰 중 먼저 온 답을 쓰고, 다른 쪽에서는 질문이 사라진다 (사용자 결정).
    - 검토 직렬화는 질문을 기다리는 동안 유지하지 않는다. `ask_user`가 나오면 검토 차례를 놓아 다른 워커의 검토가 계속되게 한다. 질문을 일으킨 요청은 답이 올 때까지 보류한다 (작성자 판단).
    - 답을 기다리는 동안 관련 워커(총괄 답의 `workers` 필드로 지정, 비었으면 요청한 워커만 해당)는 진행 중인 차례를 끊지 않고 다음 차례만 보류하며, 나머지는 계속 일한다. 총괄이 명시적으로 워커 메시지를 보내면 그때만 `AgentLine.deliver`로 차례를 끊는다 (작성자 판단).
    - 질문에는 시간 제한이 없고 작업을 중지하면 사라진다 (작성자 판단).

### 6.7 오른쪽 창 (사용자 결정: A안)
- 내용 구성은 시안대로 위에서부터:
    1. 총괄 카드: 병렬 작업 모드에서 작업이 시작되면 보인다 (작성자 판단). 상태, 질문, 전체 지시 칸.
    2. 워커 카드: 2열, 상태, 현재 활동, 총괄에게 알리기, 중지, 별도 창 열기.
    3. 게임 테스트 대기열: 실행 중 항목에 그 테스트만 끄는 버튼을 둔다 (사용자 결정).
    4. 총괄의 명령 판단 기록: 사용자가 "모든 명령 자동 허용"과 "비슷한 명령" 규칙을 끄는 버튼을 둔다 (작성자 판단).
- 창을 넓혀도 대화가 가려지지 않게 `.app` 열 폭을 패널 폭만큼 넓히는 방식으로 바꾼다. 폭의 최소·최대값은 구현자 결정이며, 값은 저장해 다음 실행에 복원한다.

### 6.8 워커 별도 창 (사용자 결정)
- 워커 카드에서 여는 Tauri `WebviewWindow`. 같은 워커는 창 하나만 열고 다시 누르면 앞으로 가져온다.
- 메인 창과 같은 `tokens.css`, `styles.css`, 테마를 쓰고 테마 변경을 따른다.
- 내용: 생성 내용, 도구 활동, 담당 파일, 요청·판단 상태, 총괄에게 알리기, 중지.
- 창을 닫아도 워커는 멈추지 않는다. 작업이 끝나도 창은 결과를 보여 주며 남아 있고 사용자가 닫는다 (작성자 판단).
- 메인 창을 닫으면 지금처럼 앱을 종료한다. 워커 창도 닫히고 실행 중인 작업·테스트는 중지와 같게 트리째 끝낸다. 메인 창에 닫기 처리를 추가해야 한다(지금 `src-tauri`에 닫기·종료 처리가 없음) (작성자 판단).
- 열 때 지금까지의 출력을 메인 창 상태에서 받아 채우고 이후 이벤트를 따른다. 메인 창 상태의 출력 상한(생성 내용 20,000자, 활동 최근 6개, `src/store.tsx`)을 그대로 두면 늦게 연 창의 이력이 잘린다. 별도 창용으로 메인 창이 워커별 출력을 더 길게 보관한다. 상한 값은 구현자 결정이며 잘렸으면 잘렸다고 표시한다 (작성자 판단).

### 6.9 워커 그룹
- 구성 (사용자 결정): 요청문에 "워커 1·2는 한 그룹"처럼 직접 적었으면 그대로 묶는다. 알아서 하라고 했으면 총괄이 묶는다.
- 그룹을 언급하지 않은 요청은 알아서 하라고 한 것과 같게 총괄이 판단한다. 서로 많이 얽힌 작업만 묶고, 나머지는 지금처럼 워커 하나가 맡는다 (작성자 판단).
- 구성 방법 (작성자 판단): 나누는 단계의 총괄이 요청문을 읽고 정한다. `split_prompt`에 "요청문에 적힌 그룹은 그대로 따를 것"을 넣고, `Part`에 `members`(기본 1)를 추가한다. 글 형식이 다양해서 정규식으로 그룹을 읽지 않는다. 전체 워커 수 상한은 지금의 `intent::MAX_AGENTS`를 따르고 그룹은 둘 이상이다. JEV는 총괄이 나눈 결과에 대해 사용자가 적은 그룹이 지켜졌는지 판단하고, 어긋나면 총괄에게 다시 나누게 한다.
- 작업 공간 (작성자 판단): 그룹 하나가 하위 작업 하나를 맡고, 그룹원은 작업 공간(사본 또는 worktree) 하나를 함께 쓴다. 그룹이 끝나면 다른 하위 작업과 같은 방식으로 바뀐 파일을 합친다.
- 진행 (작성자 판단): 회의 모드의 라운드 구조를 파일 작업으로 넓힌다. 첫 라운드는 파일을 고치지 않고 역할과 맡을 파일을 정한다. 다음 라운드부터 그룹원이 동시에 일한다. 각 차례 끝에 ```` ```elysium-group ```` 펜스 블록으로 JSON을 낸다: `{"say":"그룹에 전할 말","claim":["맡는 파일"],"done":false}`. 다음 차례 프롬프트로 다른 그룹원의 글을 전달한다(`COUNCIL_MSG_CHARS`로 자른다). `resumable()`이 아닌 엔진은 전체 기록을 다시 받는다.
- 파일 겹침 (작성자 판단): 같은 라운드에 두 그룹원이 같은 파일을 `claim`하면 나중에 낸 그룹원의 다음 차례를 보류하고 둘에게 정리하라고 알린다. 다른 그룹원은 계속 일한다.
- 끝나는 조건 (작성자 판단): 모든 그룹원이 `done`이면 끝난다. 라운드 상한(값은 구현자 결정)을 둔다. JEV가 라운드마다 그룹이 막혔는지 판단하고, 막혔으면 총괄을 부른다. 총괄은 그룹에 메시지를 보내거나 사용자에게 질문할 수 있다.
- 결과 (작성자 판단): 끝나면 그룹의 첫 번째 그룹원이 결과를 정리해 총괄에게 넘긴다. 그룹원 일부가 실패해도 남은 그룹원이 이어 간다.
- 명령·게임 테스트: 그룹원도 6.1~6.5와 같이 요청한다. 현재 폴더는 그룹의 공용 작업 공간이다.
- 소통 (작성자 판단): 사용자는 그룹 카드에서 그룹 전체 또는 그룹원 문제를 총괄에게 알린다. 그룹원을 하나씩 또는 그룹 전체로 중지할 수 있다.
- 화면 (작성자 판단): 오른쪽 창의 워커 카드 자리에 그룹 카드를 보인다. 상태, 그룹원, 최근 대화, 총괄에게 알리기, 중지, 별도 창 열기를 둔다. 그룹도 6.8과 같은 별도 OS 창으로 띄울 수 있고 그룹 대화를 실시간으로 보여 준다. 그룹 대화는 작업이 끝나도 `message_data`에 저장한다.

## 7. 구현자에게 맡기는 것
- 모듈 분리와 이름(권장: 정책과 파서를 순수 함수 모듈로 분리해 단위 테스트), JEV 임계값, 차례 수 상한, 시간 제한 범위, 별도 창 라우팅 방식, 창 위치 기억 여부, 패널 폭 범위.
- 원격 총괄 질문 조회·답변 경로 이름(`src-tauri/src/remote.rs`).
- 게임 테스트 `timeout_sec` 상한 값(Plexus `frameBenchmark`의 창 12번, 창 사이 20초 대기 완료 가능 조건 충족).
- 별도 창용 워커별 출력 보관 상한 값.
- 그룹 라운드 상한, 그룹 프로토콜의 세부 필드 이름.

## 8. 확인 방법
- 단위 테스트: 요청 블록 파싱과 제거, 규칙 일치와 이어 붙인 명령 거부, 위험한 패턴 낮춤, 대기열 순서와 용량 변경, 판단 JSON 해석 실패 시 거부, 그룹 블록 파싱, `members` 파싱, 파일 겹침 판정.
- 실제 `agy` 및 환경 시험:
    - 요청, 총괄 검토, 실행, 재개 왕복.
    - 대기열이 찬 상태에서 다른 일을 먼저 하는지.
    - 중지 시 프로세스 트리 종료.
    - 게임 강제 종료 시험: Plexus Gradle 데몬의 게임 자식 프로세스가 PowerShell 트리 종료로 끝나는지 실제 시험하고, 필요시 `--no-daemon` 적용 및 감사 기록 확인.
    - 대기열 카드의 게임 테스트 개별 종료 버튼 동작(워커 미중지, 사용자 종료 결과 전달).
    - 요청문에 적은 그룹이 그대로 묶이는지, 그룹을 언급하지 않았을 때 총괄이 묶는지, 두 그룹원이 역할을 나눠 같은 작업 공간에서 파일을 고치고 대화가 이어지는지.
