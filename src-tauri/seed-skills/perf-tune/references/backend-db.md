# 서버·API·데이터베이스 성능

## 목표 출발점
- 사용자가 기다리는 API: p95 200~500ms, 변경 요청(저장 등)은 500ms 안에 응답.
- 배치·백그라운드 작업: 처리량(건/초)과 전체 시간으로 목표.

## 요청 한 건을 구간으로 나누기
요청 → 인증 → 입력 검증 → DB/외부 호출 → 계산 → 직렬화 → 응답. 구간마다 시간을 찍어 가장 큰 구간부터.

## 데이터베이스
- **N+1**: 목록 하나에 항목마다 쿼리. → 한 번에 가져오기(JOIN, `IN (...)`, ORM의 eager loading·prefetch).
- **인덱스**: `WHERE`·`JOIN`·`ORDER BY`에 쓰는 열. 복합 인덱스는 같음 조건 열 먼저, 범위 조건 나중. 실행 계획으로 실제 사용 확인(전체 스캔 → 인덱스 스캔).
- 필요한 열만 고르기(`SELECT *` 피하기), 큰 결과는 페이지 나누기(키셋 방식이 OFFSET보다 빠름).
- 쓰기 많은 경우: 일괄 삽입, 트랜잭션으로 묶기, 불필요한 인덱스 줄이기.
- 잠금·교착: 트랜잭션을 짧게, 같은 순서로 잠그기.
- 연결 풀 크기 확인(너무 작으면 대기, 너무 크면 DB 과부하).
- SQLite: WAL 모드, 트랜잭션 묶기, `PRAGMA` 확인, 인덱스는 `EXPLAIN QUERY PLAN`으로.

## 캐시
- 어디에: 계산 결과(메모리), 자주 읽는 데이터(Redis 등), HTTP 응답(CDN·ETag), 클라이언트.
- **무효화 규칙을 같이 정하기**: 언제 지우는지(시간·변경 이벤트), 크기 상한, 지워졌을 때 몰리는 요청(cache stampede) 막기.
- 캐시 적중률을 재세요. 적중률이 낮은 캐시는 복잡함만 늘립니다.

## I/O와 동시성
- 막는 I/O를 비동기로, 서로 독립인 외부 호출은 동시에.
- 외부 호출에는 시간 제한·재시도(지수 대기)·회로 차단.
- 느린 일은 큐로 넘기고 바로 응답(이메일, 썸네일, 보고서).
- 직렬화가 크면 필요한 필드만, 압축(gzip/br), 스트리밍 응답.

## 메모리 누수·증가
- 시간에 따라 계속 느는지 확인(그래프). 힙 덤프 두 번 비교.
- 흔한 원인: 끝없이 커지는 전역 캐시·맵, 지우지 않은 리스너·타이머, 큰 객체를 붙잡는 클로저, 연결 누수.

## 부하 시험
- 실제 비율에 가까운 요청 섞기, 서서히 올리며 p95가 꺾이는 지점과 오류율 보기.
- 병목이 CPU·메모리·DB·네트워크 중 어디인지 자원 사용률을 같이 기록.
