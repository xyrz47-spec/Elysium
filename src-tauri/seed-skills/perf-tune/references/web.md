# 웹 화면 성능

## 기준(실제 사용자 75번째 백분위)
| 지표 | 좋음 | 나쁨 |
|---|---|---|
| LCP 가장 큰 내용 그리기 | ≤ 2.5초 | > 4초 |
| INP 입력 반응 | ≤ 200ms | > 500ms |
| CLS 화면 밀림 | ≤ 0.1 | > 0.25 |
| TTFB 첫 바이트 | ≤ 0.8초 | > 1.8초 |
예산 출발점: 페이지 1.5MB, 압축 JS 300KB, CSS 100KB, 첫 화면 이미지 500KB, 글꼴 100KB, 외부 코드 200KB.

## LCP가 나쁠 때(순서대로 확인)
1. 서버 응답(TTFB): 캐시(CDN·서버), 느린 쿼리, 리다이렉트 줄이기.
2. LCP 요소 찾기(DevTools): 대개 히어로 이미지나 큰 제목.
3. 이미지면: 미리 불러오기(`fetchpriority="high"`), 지연 불러오기 끄기, 크기 줄이기(srcset·AVIF/WebP), CDN.
4. 글이면: 글꼴 미리 불러오기, `font-display: swap`, 부분 집합.
5. 그리기를 막는 CSS·JS: 중요한 CSS만 먼저, 나머지 JS는 `defer`, 외부 스크립트 늦게.
6. 클라이언트에서만 그리는 화면이면 서버 렌더·정적 생성 검토.

## INP가 나쁠 때
- 50ms 넘는 긴 작업을 찾아 쪼개기(`scheduler.yield()`·`setTimeout`·`requestIdleCallback`).
- 이벤트 처리기에서 무거운 일을 빼고, 화면 갱신을 먼저 한 뒤 나머지를 미루기.
- 큰 목록 다시 그리기 줄이기(가상화, memo는 측정 후), 비싼 계산은 Web Worker로.
- 외부 스크립트(분석·광고)가 메인 스레드를 잡는지 확인.

## CLS가 나쁠 때
- 이미지·영상·광고·임베드에 크기(width/height 또는 aspect-ratio) 지정.
- 나중에 위쪽에 끼워 넣는 배너·알림 대신 자리를 미리 잡거나 아래·위에 겹쳐 띄우기.
- 글꼴 교체로 밀리면 비슷한 대체 글꼴 크기 맞춤(`size-adjust`).
- 애니메이션은 transform으로(레이아웃 속성 금지).

## 번들·불러오기
- 경로별 코드 나누기, 무거운 라이브러리는 쓰는 순간에 `import()`.
- 묶음(barrel) 파일에서 통째로 가져오지 말고 직접 경로로(트리 셰이킹이 안 되는 경우가 많음).
- 같은 라이브러리 중복 버전 확인(번들 분석기).
- 정적 파일은 긴 캐시 + 이름에 해시, HTML은 짧은 캐시.
- 필요한 외부 출처는 `preconnect`.

## React·Next.js 우선순위(높은 것부터)
1. 순차 대기(waterfall) 없애기: 서로 독립인 요청은 동시에(`Promise.all`), await는 정말 필요한 곳에서, Suspense로 화면 나누기.
2. 번들 크기: 동적 import, 직접 경로 import, 외부 코드 늦게.
3. 서버: 같은 요청 캐시·중복 제거, 클라이언트로 넘기는 데이터 최소화, 응답 뒤로 미룰 일은 미루기.
4. 클라이언트 데이터: 같은 요청·리스너 중복 제거(SWR·React Query 등).
5. 다시 그리기: 계산 가능한 값은 상태로 두지 않기(effect로 맞추지 않기), 컴포넌트 안에서 컴포넌트 정의 금지, 측정 후 memo.
6. 그리기: `content-visibility`, 변하지 않는 JSX는 밖으로, 느린 갱신은 `useTransition`.
7. JS 미세 최적화: 뜨거운 경로에서만(Map/Set 조회, 반복 합치기).

## 메모리(브라우저)
- 힙 스냅샷을 두 번(동작 전·후) 찍어 늘어난 객체 찾기. 흔한 원인: 지우지 않은 이벤트 리스너·타이머·구독, 전역 캐시, 분리된 DOM.
