# 성능 개선

**원칙: 재지 않은 것은 고치지 않는다. 고친 뒤 다시 재지 않은 것은 고쳤다고 말하지 않는다.**
추측으로 여러 곳을 한꺼번에 바꾸면 무엇이 효과였는지 알 수 없고, 버그만 늘어납니다.

자세한 방법은 참고 파일에 있습니다. 해당 단계에서 필요한 것만 여세요.

## 1. 문제를 숫자로 정하기
- 무엇이(어떤 화면·요청·명령·작업이) 어떤 조건에서(데이터 크기, 기기, 동시 사용자) 얼마나 느린지.
  예) "주문 목록 API, 주문 1만 건, p95 1.8초" / "첫 화면 LCP 4.1초(휴대폰, 4G)" / "빌드 6분"
- **목표**를 정하세요. 사용자가 말하지 않았으면 합리적인 목표를 제안하고 그렇다고 밝히세요(`references/web.md`, `references/backend-db.md`의 기준 참고).
- 정확도·기능이 바뀌면 안 된다는 것을 확인할 테스트나 비교 방법을 먼저 정하세요.

## 2. 기준선 재기 → `references/measure.md`
- 다시 똑같이 잴 수 있는 방법(명령·스크립트·데이터·반복 횟수)을 적고, 데우기(warm-up) 후 3~10번 재서 중간값과 p95를 쓰세요.
- 흔들림(편차)이 크면 먼저 그 원인(캐시, 다른 프로그램, 전원 모드)을 줄이세요. 편차보다 작은 개선은 개선이 아닙니다.
- 직접 잴 수 없는 환경이면(실행 불가 등) 어떻게 재면 되는지 명령을 주고, 코드에서 보이는 의심 지점은 "가설"로만 표시하세요.

## 3. 병목 찾기
- 프로파일러(플레임 그래프)·추적·쿼리 계획·로그 타이머로 **시간이 실제로 쓰이는 곳**을 찾으세요. 전체의 몇 %를 차지하는지 적으세요.
- 가장 큰 한 곳부터. 10%를 차지하는 곳을 두 배 빠르게 해도 전체는 5%만 줄어듭니다(암달의 법칙).
- 흔한 원인 목록: 반복문 안의 I/O·쿼리(N+1), 인덱스 없는 검색, 같은 계산 반복, 큰 데이터 통째 복사·직렬화, 동기 I/O로 막힘, 캐시 없음 또는 캐시 무효화 실패, 잦은 작은 요청, 잠금 경합, 메모리를 놓지 않는 참조, 불필요한 다시 그리기, 큰 번들.

## 4. 분야별 처방 → `references/web.md`, `references/backend-db.md`, `references/languages.md`
- 처방은 효과가 크고 위험이 작은 것부터. 구조를 크게 바꾸는 처방은 이득을 숫자로 보인 뒤에.
- 캐시를 넣으면 **무효화 규칙**(언제 지우는지)과 메모리 상한을 같이 정하세요.
- 병렬화는 마지막 수단: 경합·순서 버그가 생기기 쉽습니다. 측정 후에.

## 5. 하나씩 고치고 다시 재기
- 한 번에 하나만 바꾸고, 2번과 **같은 방법**으로 다시 재세요. 좋아지지 않았으면 되돌리세요.
- 테스트로 결과가 같은지 확인하세요(정확도 > 속도).
- 읽기 어려워지는 최적화는 이득이 클 때만, 주석으로 이유와 측정값을 남기세요.
- 목표에 닿으면 멈추세요. 목표를 넘는 미세 최적화는 유지 비용만 늘립니다.

## 출력 형식 → `references/report.md`
| 항목 | 전 | 후 | 변화 | 잰 방법 |
|---|---|---|---|---|
- 원인 한 줄(가장 큰 병목과 비중), 바꾼 것(파일·핵심 줄), 정확도 확인 결과
- 남은 병목과 다음 후보(예상 효과 순), 재지 못한 것은 "측정 안 함"
