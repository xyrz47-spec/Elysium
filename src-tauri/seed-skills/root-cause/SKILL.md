# 근본 원인 찾기

**원칙 1: 원인을 찾기 전에는 고치지 않는다.** 증상만 덮는 수정은 다른 곳에서 다시 터집니다.
**원칙 2: 증거 없이 "고쳤다"고 말하지 않는다.** 원래 증상을 다시 실행해 사라진 것을 보여야 고친 것입니다.

## 1단계: 원인 조사(고치기 전에 반드시)
1. **오류를 끝까지 읽기**: 메시지, 스택 추적 전체, 파일·줄·오류 코드. 경고도 무시하지 않기. 답이 거기 있는 경우가 많습니다.
2. **재현하기**: 정확한 단계, 매번 일어나는지, 어떤 입력·환경에서만인지. 재현이 안 되면 추측하지 말고 정보를 더 모으기(로그 추가, 사용자에게 단계 확인).
3. **최근 변경 보기**: 무엇이 바뀌었나(코드 diff, 의존성 업데이트, 설정, 환경 변수, OS·브라우저 버전).
4. **여러 부품이 이어진 경우**: 부품 경계마다 들어오고 나가는 값을 한 번 찍어서 **어디서** 틀어지는지 먼저 찾기(예: 화면 → API → 서비스 → DB).
5. **데이터 거꾸로 따라가기**: 잘못된 값이 처음 생긴 곳까지 호출을 거슬러 올라가기.

## 2단계: 패턴 비교
- 같은 코드에서 **잘 되는 비슷한 경우**를 찾아 차이를 하나씩 적기(입력, 설정, 순서, 시점).
- 쓰는 라이브러리·API의 공식 문서·예시와 비교. 기억이 아니라 문서로.

## 3단계: 가설 하나 세우고 검증
- "X 때문에 Y가 일어난다. 그렇다면 Z를 바꾸면 사라질 것이다"처럼 **하나의 가설**을 분명히.
- 가장 작은 실험으로 확인(변수 하나만 바꾸기). 틀렸으면 그 가설을 버리고 1단계로. 여러 수정을 겹쳐 쌓지 않기.
- 세 번 시도해도 안 되면 멈추고 구조 자체를 의심하세요(설계가 문제일 수 있음). 사용자에게 지금까지 알아낸 것을 공유하세요.

## 4단계: 고치기(테스트 먼저)
1. **실패하는 테스트 먼저**: 버그를 재현하는 가장 작은 테스트를 쓰고, 실행해서 **실패하는 것을 확인**하세요(실패를 못 보면 그 테스트는 버그를 잡지 못합니다).
2. **원인을 고치는 가장 작은 수정**: 증상이 아니라 1~3단계에서 찾은 원인을.
3. **다시 실행**: 새 테스트가 통과하고, 기존 테스트도 모두 통과하는지.
4. 같은 원인이 다른 곳에도 있는지 찾아보기.

## 5단계: 완료라고 말하기 전에
| 말하려는 것 | 필요한 증거 | 증거가 아닌 것 |
|---|---|---|
| 테스트 통과 | 방금 실행한 테스트 출력: 실패 0 | 예전 실행, "통과할 것" |
| 빌드 성공 | 빌드 명령 종료 코드 0 | 린트 통과, 로그가 괜찮아 보임 |
| 버그 고침 | 원래 증상을 다시 해 봤더니 사라짐 | 코드를 바꿨음 |
| 회귀 테스트 | 고치기 전 실패 → 고친 뒤 통과를 둘 다 봄 | 한 번 통과 |
- "아마", "~일 것", "될 것 같다"가 떠오르면 멈추고 실행해서 확인하세요.
- 실행할 수 없는 환경이면 "확인하지 못함"과 확인 명령을 적으세요.

## 출력 형식
1. **원인**: 한두 문장(어디서, 왜) + 근거(로그·재현 결과)
2. **재현**: 단계 또는 테스트
3. **수정**: 바꾼 파일·줄과 이유
4. **확인**: 실행한 명령과 결과(실패 → 통과), 확인하지 못한 것
5. **예방**(있으면): 같은 일이 다시 생기지 않게 할 것
