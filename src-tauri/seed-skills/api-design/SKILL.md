# API 설계

사용자의 요구사항이나 기존 명세를 바탕으로 REST, GraphQL, RPC API를 새로 설계하거나 검토합니다.
일관된 리소스 규칙, 명확한 상태·오류 규격, 바로 구현할 수 있는 엔드포인트 표와 요청·응답 예시를 제시하세요.

## 1. 시작 전 확인할 것
- 요청에서 **도메인(다루는 데이터)**, **주요 동작(조회·생성·상태 변경)**, **API 스타일(REST·GraphQL·RPC)**을 먼저 파악하세요.
- 스타일이 지정되지 않았다면 일반 CRUD·리소스 중심은 REST, 복합 조회·클라이언트 주도 스키마는 GraphQL, 내부 서비스 간 고성능 호출·동작 중심은 RPC(gRPC 등)를 기본으로 제안하고 이유를 한 줄로 밝히세요.
- 기존 코드나 API 문서가 주어졌다면 명명 규칙(camelCase/snake_case), 버전 체계, 인증 방식을 먼저 읽고 그대로 따르세요.
- 도메인 핵심 엔티티나 호출 주체(공개 API·내부 백엔드·모바일 등)를 전혀 알 수 없을 때만 **꼭 필요한 질문 1~2개**를 먼저 묻고, 나머지는 합리적인 기본값으로 설계한 뒤 가정한 사항을 명시하세요.

## 2. 설계 및 검토 절차
- **리소스 및 경로 명명**: REST 경로는 복수형 명사(`/v1/orders`, `/v1/orders/{orderId}/items`)로 쓰고 동사를 넣지 마세요. 비CRUD 동작은 하위 리소스나 명확한 동작 경로(`POST /v1/orders/{orderId}/cancel`)로 분리하세요. GraphQL은 조회(`Query`)와 변경(`Mutation`) 이름을 명확히 구분하고, RPC는 `Service.VerbNoun` 형식을 지키세요.
- **HTTP 메서드와 상태 코드**: 용도에 맞게 메서드(`GET` 조회, `POST` 생성·실행, `PUT` 전체 교체, `PATCH` 부분 수정, `DELETE` 삭제)를 배정하세요. 상태 코드는 실제 의미에 맞춰 구체적으로 지정하세요(`200 OK`, `201 Created`, `202 Accepted`, `204 No Content`, `400 Bad Request`, `401 Unauthorized`, `403 Forbidden`, `404 Not Found`, `409 Conflict`, `422 Unprocessable Entity`, `429 Too Many Requests`).
- **목록 조회(페이지네이션·필터링·정렬)**: 목록 API는 항상 페이지네이션을 포함하세요. 실시간 추가·대용량 목록은 커서 기반(`cursor`, `limit`), 페이지 번호 이동이 필요하면 오프셋 기반(`page`, `size`)을 선택하세요. 필터(`status=PAID`), 정렬(`sort=-createdAt`), 필드 선택 규격을 일관되게 정의하세요.
- **버전 관리**: 기존 클라이언트가 깨지는 변경(필드 삭제, 타입 변경, 필수값 추가)은 새 버전(`/v1/`, 헤더 버전, 또는 스키마 `@deprecated`)으로 분리하는 전략을 명시하세요.
- **표준 오류 형식**: 모든 오류 응답이 동일한 JSON 구조(`code`, `message`, `details`, `requestId` 등)를 쓰도록 정의하세요.
- **멱등성(Idempotency)**: 결제·주문·외부 발송처럼 중복 실행되면 위험한 `POST`/`PATCH` 요청에는 `Idempotency-Key` 헤더 처리 방식과 재시도 시 동작을 반드시 포함하세요.
- **인증·인가 및 호출 제한(Rate Limit)**: 인증 방식(Bearer JWT, API Key, OAuth2, mTLS)과 권한 검사 기준(소유자 확인, 역할 기반)을 적으세요. 호출 제한 기준과 초과 시 응답 헤더(`Retry-After`, `X-RateLimit-Remaining`)를 명시하세요.

## 3. 품질 규칙 및 하지 말아야 할 것
- 모든 요청을 `200 OK`로 돌려주고 본문 안의 `success: false`로만 실패를 구분하는 설계(GraphQL 표준 규격 제외)는 피하고, 기존 명세에 있다면 문제점으로 지적하세요.
- 데이터베이스 테이블 구조나 내부 구현 컬럼(예: 비밀번호 해시, 내부 전용 플래그)을 응답에 그대로 노출하지 마세요.
- 정수 증가형 ID 노출 시 권한 없는 타인 리소스 접근(BOLA/IDOR) 위험을 짚고, 소유권 검증이나 외부용 식별자(UUID/ULID) 사용을 권장하세요.
- 확인되지 않은 외부 서비스의 실제 제한 수치, 요금, 공식 SDK 스펙을 지어내지 마세요. 불확실한 외부 규격은 "확실하지 않음 — 공식 문서 확인 필요"로 남기세요.
- 필드 타입(문자열, 정수, ISO 8601 시각 `2026-11-04T09:00:00Z`, 금액의 통화·소수점 처리)과 필수/선택 여부, `null` 허용 여부를 모호하게 두지 마세요.

## 4. 출력 형식
아래 순서와 구성을 기본으로 답하세요. 부분 검토 요청이면 해당되는 항목만 간결하게 쓰세요.

### 1) 설계 원칙 요약
- 스타일·버전·인증·페이지네이션·멱등성·호출 제한 기준을 각 한 줄로 정리합니다.

### 2) 엔드포인트(또는 스키마·메서드) 요약 표
| 구분/메서드 | 경로 또는 이름 | 설명 | 인증/권한 | 멱등성 | 성공/주요 오류 코드 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| POST | `/v1/orders` | 주문 생성 | Bearer (User) | `Idempotency-Key` 필수 | `201`, `400`, `409`, `422` |
| GET | `/v1/orders` | 주문 목록 조회 | Bearer (User) | 자연 멱등 | `200`, `401`, `429` |

### 3) 핵심 요청·응답 및 오류 예시
- 가장 중요한 엔드포인트 1~2개의 요청(헤더·쿼리·본문)과 성공 응답(`200`/`201`), 표준 오류 응답(`4xx`) JSON 예시를 함께 제시하세요.
- 검토 요청일 때는 **발견된 문제(심각도 순) → 바꿀 설계안** 순서로 정리하세요.
