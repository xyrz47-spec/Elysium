# 커밋 메시지 작성

사용자의 변경 내역(diff)이나 작업 설명을 바탕으로 **Conventional Commits** 규격의 명확한 Git 커밋 메시지를 작성합니다.
무엇을 바꿨는지보다 **왜 바꿨는지**가 드러나도록 쓰고, 저장소의 기존 커밋 언어와 문체를 따르세요.

## 1. 먼저 확인할 것
- **변경 입력 확인**: 사용자가 전달한 `git diff`, 변경 파일 목록, 또는 작업 설명을 먼저 살핍니다.
- **저장소 기록 확인(가능할 때)**: 작업 경로를 읽을 수 있고 사용자가 diff를 직접 주지 않았다면 `git status`와 `git diff --staged`(비어 있으면 `git diff`)를 확인하고, `git log -n 10 --oneline`으로 최근 커밋의 언어(한국어·영어), 스코프 표기 방식, 문체를 파악하세요.
- **꼭 필요한 질문만 하기**: 변경 내용도 없고 저장소도 읽을 수 없을 때만 "어떤 변경을 커밋하시나요?"라고 한 줄로 물으세요. 변경 이유나 이슈 번호를 알 수 없으면 추측해 묻기보다 확인된 내용만으로 메시지를 먼저 작성하고 필요한 부분만 짧게 안내하세요.

## 2. 작성 절차
- **1단계 — 변경 단위 점검**: 한 커밋에 서로 무관한 변경(기능 추가와 단순 포맷 정리 등)이 섞여 있으면 커밋을 나누는 안을 함께 제안하세요.
- **2단계 — 타입(type) 선택**: 변경의 핵심 목적에 맞춰 하나를 고릅니다.
  - `feat`: 새로운 기능 추가
  - `fix`: 버그 수정
  - `refactor`: 동작 변경 없는 코드 구조 개선
  - `perf`: 성능 개선
  - `docs`: 문서 추가·수정
  - `test`: 테스트 코드 추가·수정
  - `build` / `ci`: 빌드 설정, 의존성, CI 파이프라인 변경
  - `chore`: 기타 유지보수 작업
- **3단계 — 스코프(scope) 결정**: 변경이 집중된 모듈·폴더·컴포넌트 이름을 괄호 안에 적습니다. 저장소에서 스코프를 쓰지 않거나 변경 범위가 넓으면 생략하세요.
- **4단계 — 제목(summary) 작성**: `type(scope): 요약` 형식으로 **72자 이내**(한글 기준 35~40자 권장)로 씁니다. 끝에 마침표를 찍지 말고, 저장소 관례에 맞는 명사형·명령형(영문일 때는 동사 원형 소문자 시작)으로 통일하세요.
- **5단계 — 본문(body) 작성**: 제목과 빈 줄 하나를 둔 뒤, 코드만 봐서는 알기 어려운 **변경 이유(why)**, 문제 원인, 핵심 결정 사항을 1~4줄로 적습니다. 단순 오타나 사소한 수정이면 본문을 생략하세요.
- **6단계 — 꼬리말(footer) 작성**: 하위 호환성이 깨지는 변경이면 타입·스코프 뒤에 `!`를 붙이고 꼬리말에 `BREAKING CHANGE: 변경 내용과 전환 방법`을 적습니다. 사용자가 알려 준 이슈·PR 번호가 있을 때만 `Closes #123`, `Refs #456` 형식으로 덧붙이세요.

## 3. 품질 규칙과 하지 말아야 할 것
- **사실만 적기**: 확인되지 않은 이슈 번호, 티켓 ID, 성능 수치, 변경 배경을 절대 지어내지 마세요. 변경 이유를 코드만으로 확신할 수 없으면 추정임을 밝히거나 비워 두세요.
- **코드 변경의 단순 나열 금지**: 본문에 바뀐 함수·변수 이름을 그대로 옮겨 적거나 "A 파일을 수정함"처럼 diff만 봐도 아는 내용을 되풀이하지 마세요.
- **언어와 문체 일치**: 최근 커밋 기록이 영어면 영어로, 한국어면 한국어로 작성합니다. 기존 기록을 알 수 없을 때는 사용자가 요청한 언어를 따르세요.
- **모호한 제목 금지**: `fix: 버그 수정`, `chore: 코드 정리`처럼 무엇이 달라졌는지 알 수 없는 제목은 쓰지 마세요.
- **72자 제한 준수**: 제목 줄이 길어지면 세부 설명은 모두 본문으로 내리세요.

## 4. 출력 형식
머리말이나 인사말 없이 바로 복사해 쓸 수 있는 커밋 메시지를 먼저 제시하세요. 변경이 복잡할 때만 대안 제목 1~2개나 커밋 분리 제안을 아래에 짧게 덧붙입니다.

- **기본 구성 템플릿**
  - 제목 줄: `<type>(<scope>): <72자 이내 핵심 요약>`
  - 빈 줄 1개
  - 본문(필요할 때만):
    - `<왜 바꿨는지: 기존 문제나 배경>`
    - `<어떻게 해결했는지: 핵심 접근 방식이나 주의점>`
  - 빈 줄 1개
  - 꼬리말(해당할 때만):
    - `BREAKING CHANGE: <호환성이 깨지는 지점과 마이그레이션 방법>`
    - `Closes #<이슈번호>`

- **작성 예시**
  - 제목: `fix(auth): 만료된 리프레시 토큰 재요청 시 무한 루프 방지`
  - 본문:
    - 리프레시 토큰까지 만료된 상태에서 401 응답을 받으면 재발급 요청이 반복 호출되는 문제가 있었음
    - 재발급 엔드포인트에서 발생한 401 응답은 재시도 대상에서 제외하고 즉시 세션을 초기화하도록 수정
