# 안전한 리팩터링

이 스킬의 목표는 **외부에서 관찰 가능한 동작을 바꾸지 않고** 코드의 가독성, 중복, 구조를 개선하는 것입니다.
기능 추가, 스펙 변경, 버그 수정은 리팩터링과 섞지 말고 분리하세요.

## 1. 시작 전 확인할 것
- 리팩터링할 대상(파일, 모듈, 클래스, 함수)이 명확한지 먼저 확인하세요.
- 정리 목적(중복 제거, 긴 함수 분리, 이름 개선, 조건문 단순화, 결합도 낮추기 등)을 파악하세요.
- 대상 코드나 경로가 아예 없거나, 보존해야 할 범위가 불분명할 때만 꼭 필요한 질문을 한두 개로 짧게 물으세요.
- 호출부 전체를 확인할 수 없는 공개 인터페이스(export 심볼, 함수 시그니처, 공개 타입, 설정 키, 직렬화·응답 형식)를 먼저 식별하세요.
- 요청 안에 동작 변경이 섞여 있으면 바로 수정하지 말고, 순수 리팩터링만 먼저 진행할지 동작 변경까지 할지 사용자에게 먼저 확인하세요.

## 2. 단계별 절차
- **1단계(기준선 확인)**: 코드를 고치기 전에 기존 테스트, 타입 검사, 린트, 빌드 명령을 먼저 실행해 현재 상태를 확인하세요. 실행할 수 없다면 그 이유와 미확인 범위를 숨기지 말고 밝히세요.
- **2단계(보존 경계 고정)**: 유지해야 할 공개 인터페이스, 입력·출력 형태, 예외·오류 처리 조건, 부수효과(입출력·상태 변경·호출 순서)를 기준선으로 정리하세요.
- **3단계(작은 단계로 분해)**: 한 번에 한 종류의 변환만 수행하도록 작업을 쪼개세요(예: 이름 변경 → 보조 함수 추출 → 중복 구문 통합 → 불필요한 분기 정리).
- **4단계(단계별 수정 및 설명)**: 각 단계를 적용할 때 무엇을 왜 바꿨는지, 왜 기존 동작과 동일한지 짧게 설명하세요.
- **5단계(단계별 재검증)**: 각 단계 직후 관련 테스트나 타입 검사를 다시 실행해 기준선과 같은 결과가 나오는지 확인하세요.
- **6단계(실패 시 즉시 복구)**: 테스트나 검사가 깨지면 다음 단계로 넘어가지 말고, 즉시 원인을 고치거나 해당 단계를 되돌리세요.
- **7단계(최종 점검)**: 작업이 끝나면 전체 변경분(diff)을 다시 읽고, 의도하지 않은 동작 변화나 범위 밖 수정이 섞이지 않았는지 확인하세요.

## 3. 품질 규칙과 절대 하지 말 것
- **공개 인터페이스 유지**: 사용자가 명시적으로 요청하지 않은 한 공개 함수·메서드 이름, 매개변수 순서와 기본값, 반환 타입과 구조는 그대로 두세요.
- **동작 변경 시 즉시 중단 후 질문**: 경계값 처리, null·예외 흐름, 정렬·반올림 규칙, 비동기 실행 순서가 달라질 수 있는 지점을 만나면 임의로 바꾸지 말고 멈춰서 사용자에게 물으세요.
- **버그 수정·기능 추가 혼합 금지**: 리팩터링 중 잠재 버그나 개선점을 발견해도 같은 변경에 몰래 섞지 말고, 별도 항목으로만 알려 주세요.
- **추측과 날조 금지**: 실행하지 않은 테스트나 빌드를 통과했다고 쓰지 마세요. 호출부나 런타임 영향을 끝까지 확인하지 못했다면 불확실한 부분을 그대로 적으세요.
- **과도한 추상화 금지**: 지금 있는 중복과 복잡도를 줄이는 데 필요한 만큼만 고치세요. 쓰이지 않는 확장성, 불필요한 래퍼, 과한 계층 분리를 새로 만들지 마세요.
- **무관한 변경 금지**: 요청 범위 밖 파일의 줄바꿈·포맷팅 수정, 기존 주석 임의 삭제, 관련 없는 import 정리를 섞지 마세요.

## 4. 출력 형식
응답은 아래 항목 순서로 간결하게 작성하세요.

- **대상 및 보존 기준**
  - 대상 파일·심볼: 리팩터링한 범위
  - 유지한 공개 인터페이스·동작: 바뀌지 않도록 고정한 시그니처와 입출력 규칙
- **사전 검증**
  - 실행한 테스트·검사 명령과 실제 결과(실행하지 못했다면 사유와 미확인 범위)
- **단계별 변경 내역**
  - `1단계 — [파일:위치 또는 심볼]`: 변경 내용, 변경 이유, 외부 동작이 유지되는 근거
  - `2단계 — [파일:위치 또는 심볼]`: 변경 내용, 변경 이유, 외부 동작이 유지되는 근거
- **사후 검증**
  - 변경 후 다시 실행한 테스트·검사 명령과 실제 결과
- **확인 요청 또는 분리 메모(해당할 때만)**
  - 동작이 바뀔 수 있어 멈추고 묻는 질문, 또는 리팩터링과 분리해 둔 잠재 버그·후속 작업 제안
