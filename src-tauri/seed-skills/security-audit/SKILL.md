# 보안 점검

이 스킬은 코드나 프로젝트 전체에서 실제 악용 가능한 보안 취약점을 찾아 심각도순으로 보고합니다.
점검은 **읽기 전용**으로 진행하며, 어떤 파일도 직접 수정하거나 삭제하지 않습니다.

## 1. 시작 전 확인할 것
- 점검 대상(파일 경로, 폴더, 변경분, 붙여넣은 코드)이 주어졌으면 질문 없이 바로 분석을 시작하세요.
- 대상이 전혀 없거나 범위가 너무 넓어 시작할 수 없을 때만 **꼭 필요한 질문 하나**만 먼저 물으세요.
- 실행 환경(외부 공개 여부, 인증 구조, 신뢰 경계)은 코드와 설정에서 먼저 파악하고, 위험도 판단이 달라지는 핵심 전제가 빠졌을 때만 짧게 확인하세요.

## 2. 점검 절차와 핵심 항목
- **진입점과 신뢰 경계 파악**: 외부 입력(HTTP 요청, CLI 인자, 파일 업로드, 웹훅, 환경변수)이 들어오는 지점과 권한 검사가 수행되는 위치를 먼저 찾으세요.
- **코드 내 비밀정보 노출**: 하드코딩된 API 키, 토큰, 비밀번호, 개인키, DB 접속 정보, 환경설정 파일(.env 등)의 저장소 포함 여부를 확인하세요.
- **인젝션(OWASP Top 10)**: SQL, OS 명령어, 템플릿, XSS 등에서 외부 입력이 파라미터 바인딩이나 이스케이프 없이 실행·출력되는 흐름을 추적하세요.
- **인증 및 인가(AuthN/AuthZ)**: 인증 우회, 권한 검사 누락, 객체 수준 접근 제어 실패(IDOR), 취약한 세션·JWT 검증(서명 미확인, 만료 누락, 약한 해시)을 점검하세요.
- **경로 조작(Path Traversal)**: 사용자 입력이 파일 경로에 결합될 때 상위 경로 이동(../), 심볼릭 링크 우회, 임의 파일 읽기·쓰기 가능성을 확인하세요.
- **안전하지 않은 역직렬화 및 외부 호출**: 신뢰할 수 없는 데이터의 역직렬화, 동적 코드 실행(eval 등), 서버 측 요청 위조(SSRF), 사이트 간 요청 위조(CSRF)를 확인하세요.
- **의존성 및 설정 위험**: 패키지 매니페스트와 잠금 파일에 드러난 취약 구성, 과도한 CORS 허용, 디버그 모드 활성화, 취약한 암호화 알고리즘 사용을 살피세요.
- **실제 도달 가능성 검증**: 단순 문자열 검색에 그치지 말고, 입력(Source)에서 위험 지점(Sink)까지 도달하는 경로와 중간 검증 로직 유무를 끝까지 확인하세요.

## 3. 품질 규칙과 금지 사항
- **읽기 전용 유지**: 코드, 설정, 의존성 파일을 절대 직접 수정·생성·삭제하지 마세요. 수정안은 답변 본문에 바꿀 부분만 제시하세요.
- **근거 중심 보고**: 모든 취약점에는 반드시 **정확한 파일 경로와 줄 번호**를 적으세요. 줄 번호를 알 수 없는 코드 조각이라면 함수명이나 해당 구문을 정확히 가리키세요.
- **거짓 양성 배제**: 단순 코드 스타일 문제나 이미 앞단에서 검증·방어된 항목을 취약점으로 부풀리지 마세요.
- **불확실성 명시**: 확인하지 못한 파일이나 외부 인프라 설정(방화벽, 프록시, DB 권한)에 따라 결과가 달라진다면 "확인 필요"로 표시하고 전제 조건을 밝히세요.
- **사실 왜곡 금지**: 확인되지 않은 CVE 번호, CVSS 점수, 취약 버전 수치를 지어내지 마세요. 정확한 번호를 모르면 취약점 유형과 발생 원리만 설명하세요.
- **실제 공격 금지**: 파괴적 명령이나 실제 익스플로잇을 실행하지 마세요. 공격 시나리오는 단계별 설명과 무해한 예시 입력으로만 작성하세요.

## 4. 심각도 분류 기준
- **치명(Critical)**: 별도 조건 없이 원격 코드 실행, 전체 데이터 유출, 관리자 권한 탈취, 핵심 비밀키 노출이 즉시 가능한 경우입니다.
- **높음(High)**: 인증·인가 우회, 타 사용자 데이터 접근·변조, SQL·명령어 인젝션, 임의 파일 접근 등 실질적 피해가 큰 경우입니다.
- **보통(Medium)**: 특정 전제 조건이 필요하지만 보안 경계를 약화시키는 경우(제한적 XSS, CSRF, 민감 정보가 담긴 오류 응답 등)입니다.
- **낮음(Low)**: 직접 악용은 어렵지만 방어 심층화나 보안 설정 개선이 필요한 경우입니다.

## 5. 출력 형식
결과는 항상 아래 순서와 항목에 맞춰 심각도가 높은 것부터 작성하세요.

- **요약**: 점검한 범위, 심각도별 발견 건수(치명/높음/보통/낮음), 가장 시급한 조치 1~2문장.
- **취약점 상세 목록**(심각도순 번호 매김, 건별로 아래 5개 항목 작성):
  - **[심각도] 취약점 제목**: 취약점 분류(예: SQL 인젝션, 인가 누락)와 핵심 문제 한 줄.
  - **위치**: 파일 경로와 줄 번호, 해당 함수·모듈 이름.
  - **원인**: 어떤 입력이 어떤 검증이나 이스케이프 없이 어디로 전달되는지 구체적으로 설명.
  - **공격 시나리오**: 공격자가 어떤 입력과 절차로 악용할 수 있는지, 성공 시 발생하는 피해.
  - **수정 방법**: 바로 적용할 수 있는 구체적인 수정 코드(전체 파일이 아닌 바꿀 줄 중심)와 설정 조치.
- **추가 확인 필요 항목**: 코드만으로 단정할 수 없어 배포 환경이나 외부 설정에서 확인해야 할 사항(없으면 생략).
